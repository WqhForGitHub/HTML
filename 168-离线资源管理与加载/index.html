浏览器对离线储存资源的管理与加载

面试题 17 · 离线缓存机制

两套体系

方案存储位置管理方式
AppCache (旧)浏览器独立离线缓存区manifest 清单驱动
Service Worker + Cache API (新)Cache Storage（独立于 HTTP 缓存）SW 代码拦截 fetch 自由控制
localStorage / IndexedDBOrigin 沙箱JS 主动读写

① 在线首次访问

1. 下载 HTML，解析 manifest / 注册 sw.js
2. 并行下载 manifest 中声明的所有 CACHE 资源
3. 把资源存入独立离线缓存（不占 HTTP 缓存空间）
4. 触发 cached 事件，应用进入"已缓存"状态

② 在线再次访问

1. 浏览器先用旧缓存渲染页面（保证速度）
2. 同时后台比对 manifest 是否变化（字节级）
3. 如果没变化→什么也不做
4. 如果有变化→重新下载 manifest 列表全部资源到新缓存区
5. 下载完成触发 updateready → 调 swapCache 切换
6. 用户下次刷新才使用新缓存（首次刷新仍是旧的）

③ 离线访问

1. 网络请求失败
2. 浏览器自动转向离线缓存查找
3. 命中→直接返回缓存资源
4. 未命中（NETWORK 段资源）→走 FALLBACK 后备页
5. AppCache 中 FALLBACK 配对：/api/* → /offline.html

Service Worker 怎么管理

// install：预缓存核心资源 self.addEventListener('install', e => { e.waitUntil(caches.open('v1').then(c => c.addAll(['/','/app.js']))) }) // fetch：拦截请求自定策略 self.addEventListener('fetch', e => { e.respondWith( caches.match(e.request).then(r => r || fetch(e.request)) // 也可：fetch 优先失败回退缓存、缓存优先 + 后台更新 等 ) }) // activate：清理旧缓存 self.addEventListener('activate', e => { e.waitUntil(caches.keys().then(keys => Promise.all( keys.filter(k => k !== 'v1').map(k => caches.delete(k)) ))) })

更新策略枚举

• 先缓存后更新（cache-first）：快但旧

• 先网络后缓存（network-first）：新但慢

• 后台更新（stale-while-revalidate）：先返回缓存同时后台拉新版

• 渐进式（按资源类型分别采用上述策略）

💡 浏览器关键逻辑：在线时优先缓存 + 后台 diff 版本号；离线时回退缓存 + FALLBACK。Service Worker 让这套逻辑可由 JS 自定义，更贴近实际需求。
